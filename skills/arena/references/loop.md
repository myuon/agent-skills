# ループ、内省、打ち切り

## 1ラウンドの型

1ラウンドで試す仮説は1つ。記録(`rounds.md` など)には、次の型で書く。

```markdown
## R12
### 宣言(評価の前に書いた)
- 仮説: …
- 変更点: …(戦略は新しいファイルにする)
- 判定基準: …
### 結果
数字。基準線との比較を必ず書く
### 門
通ったか。落ちたなら、どの門で
### わかったこと
仮説を閉じる。「効かなかった」も成果として書く
### 次
```

- セッションの冒頭に「このセッションで試すことのリスト」を順番つきで書き、それ以外は回さない
- 1つの仮説の変種は3つまで。超えたら閉じて次へ進む
- 効かなかった後の強さの再調整(閾値や正則化を少し変えて同じ検証で再評価する)は、検証への過適合として禁止する
- 候補に届かなかったものを、変形して同じ検証で再評価しない
- 自由パラメータは少なくする(例: 4個以下)。日付に依存するルールや、対象の手選びは禁止する

## ループを止めない

- 新しいデータ待ち、人間の返事待ち、一定件数の蓄積待ちを、採用やループ再開の条件にしない。待ちが要る確認は事後の監査として非同期に走らせ、負けたら取り消す
- 外部の点検役やリードの推奨が「待ち」を生むなら、待たない形に言い換える(例: 「新データで確認してから採用」→「採用し、新データで監査して負けたら取り消す」)
- 人間に確認したいことがあっても、ループは止めずに続け、確認事項はダッシュボードの「待ち」に書く
- データが足りないときは、待つのでなく、今のデータで系列を増やす([augmentation.md](augmentation.md))
- 早々に諦めない。途中の負けは結論ではない。改善の対象には、方策だけでなくモデル、特徴量、ラベルも含める。結論は事前登録した判定でだけ出す

## 記録

| ファイル | 中身 |
| --- | --- |
| `trials.jsonl` / `registry.jsonl` | 全評価を自動で追記。データ・凍結ファイル・コードのハッシュ、split、指標、門の結果。手で書き換えない |
| `scratch.jsonl` | 下見。これも試行回数に数える |
| `adopted.json` | split ごとの採用状態と、取り消しの履歴(理由、試行の id)。取り消した名前は再採用しない |
| `holdout_audit.jsonl` | 封印テストを開けた記録。時刻、評価した版のハッシュ、何回目か。追記のみ |
| `tried.md` | 効かなかった考えと測定値。再検討するときは「何が変わったか」を書く |
| 「崩れた前提」の表 | 大きな改善が、どの前提を崩したときに出たか |

## 内省の仕組み

振り返りを、人の気づきに頼らず仕組みにする。
- **知見の台帳**(`lessons.md` など): 仮説の種類ごとに、試した数と採用の数を集計する。毎セッションの冒頭で読む。例: 特徴量の追加は8回試して採用0、判断の水準は6回試して採用2。採用率の低い種類は後回しにする
- **言い換えの表**: 同じ考えを別の形で試したものを1行にまとめる。例: 「出す量を減らす」を4回、近傍の調整を10回
- **外部の点検役**: split の切り替えや系統の終わりに、ループに関わらない点検役(別のセッション、読むだけ)を起こす
- **ルールの変更は提案だけ**: ループ担当は手順、門、契約を自分で変えず、提案として記録に残す。採否はリードか人間が決める

## 振り返り

5〜10ラウンドごと、またはセッションの終わりに書く。
- 効いた考え、効かなかった考え
- 偶然の可能性: 試行回数、補正後の有意性、効果の大きさとノイズ幅の比
- **同じ考えの言い換えになっていないか**: 別々に見える改善が、実は同じ考え(例: 直近の強さ)を別の形で測っているだけのことが多い。それは独立の証拠ではない
- 伸びの中身: 露出の増加、相場や環境の追い風、行動の頻度の変化で説明できないか
- 次の仮説の上位3つ
- ループ自体の摩擦(遅い評価、壊れたスクリプト、手作業)。見つけたら、コード、テスト、契約まで直す

## 打ち切りと方針転換

数を埋めるために回し続けない。

- **区切りは時間か頭打ちで決める**。ラウンド数で区切るセッションを定期実行で回すより、時間の上限か頭打ちまで回し切るほうがよい。ただし最低ラウンド数(例: 50)を置き、それまでは頭打ちを判定しない(例: 30ラウンドまでは判定しない)
- **頭打ち**: 直近 K ラウンド(例: 5〜20)で採用なし、または最良の伸びが閾値未満
  - 頭打ちを学習期間の成績で判定すると、「伸びなくなるまで回す」こと自体が学習期間への合わせ込みになる。判定に使う成績と、検証は分ける
  - 学習側の評価が数百回に達したら、それ以上は偶然の上乗せが増えるだけ、と見て止める
- **試しすぎ**: 同じ split で、試行回数で補正した後に必要な z が約3を超えたら打ち切り、新しいデータを含めて split を切り直す
- **門の閾値の近く**: 採用中の候補が門の閾値のすぐ近くにあると、少しの変更で門を割る。閾値の近傍を探すのは無駄になりやすいので、探索空間そのもの(行動の種類、入力の種類)を変える
- **時間**: 1回のセッションは H 時間まで(例: 8時間)
- **ラウンド**: 上限 R(例: 200)
- **方針転換**: 一定時間(例: 60分)、または一定ラウンド門を通らなければ、調整や高速化をやめ、前提から違う方針を立てる。大きな改善は、書き出されていなかった前提を崩したときに出ることが多い。「崩れた前提」の表を、次の転換の根拠にする
- **系統のリセット**: 封印テストで不合格になったら、その系統を閉じる。戦略と記録は archive に移し、ループからは見えないようにする。試行回数のカウンタはリセットしない
- **不合格の原因を封印期間で調べない**: 原因を調べて直すと、封印期間への合わせ込みになる。原因の分析は設計用の期間でだけ行う

止めるときは「区切り」を書く。止めた理由、効いたもの、効かなかったもの、次の仮説の上位3つ。

## 並列のエージェント

- 前提が重ならない方向に3台前後を振る。同じ方向に複数を当てない
- worktree で分ける。共有の作業ツリーでは、ブランチの切り替えでコミットが混ざる事故が起きる
- 各エージェントは worktree の中で実測し、勝ったときだけブランチにコミットする。本番への提出と push はさせない
- 依頼文には共通のブリーフを使う。含めるもの: 既知の否定結果(測定値つき)、打ち切りの条件、予算、時間の上限
- 本体は報告を鵜呑みにせず、自分で再測定してから取り込む
- 別々の版から出た改善は、足し算にならないことが多い。統合は別の担当に任せ、パラメータを実測で決め直させる

## 役割の分担

| 役割 | やること |
| --- | --- |
| リード(主セッション) | 契約と門の管理、検証と封印テストの実行(事前登録の後)、人間への報告 |
| ループ担当 | 隔離した作業場所で、設計用のデータだけでラウンドを回す。ルールは変えず、提案を残す |
| 点検役 | 外から読むだけで点検し、優先順位つきの指示を出す。待ちを生む指示を出さない |

- ループ担当への指示文は版で管理し、系統ごとに別のファイルにする。汎用の指示文が、系統専用の指示を上書きしかけた事故がある
- リードが「頼みます」と言って、実際の依頼を出し忘れることがある。依頼を出したら、相手のセッションが動いたかを確かめる
- 親のプロセスが終わると、子のセッションも一緒に止まることがある。長い作業は引き継ぎのファイルを書きながら進める
- 1回のセッションの目安: 10ラウンドで数分〜数十分。文脈が苦しくなったら、台帳とラウンド記録に引き継ぎを書いて終える

## よくある事故

- 採点器のスクリプトが、分割名の変更などで落ちていて、記録が書かれていなかった。分割や名前を変えたら、参照しているコードを総点検する
- 常駐のジョブが古いブランチから起動して失敗した。主ツリーは main に固定し、作業は worktree でする
- 未コミットのコードで作ったデータセットが、再現できなくなった
- 採点器や門のコード(ループからは直せない、凍結された側)のバグで、記録のコマンドが何十ラウンドも落ちていた。ループ担当は凍結された側を直さず、リードに報告する経路を決めておく
- 試行 ID にデータの版を含めていたため、データが増えるたびに同じ設定が新しい試行として数えられ、試行回数が水増しされた。試行 ID は(コード、設定)のハッシュにする
- テストの出力を `tail` に通して、終了コードが失われた
