# ループ、内省、打ち切り

## 1ラウンドの型

1ラウンドで試す仮説は1つ。記録(`rounds.md` など)には、次の型で書く。

```markdown
## R12
### 宣言(評価の前に書いた)
- 仮説: …
- 変更点: …(戦略は新しいファイルにする)
- 判定基準: …
### 結果
数字。基準線との比較を必ず書く
### 門
通ったか。落ちたなら、どの門で
### わかったこと
仮説を閉じる。「効かなかった」も成果として書く
### 次
```

- セッションの冒頭に「このセッションで試すことのリスト」を順番つきで書き、それ以外は回さない
- 1つの仮説の変種は3つまで。超えたら閉じて次へ進む
- 効かなかった後の強さの再調整(閾値や正則化を少し変えて同じ検証で再評価する)は、検証への過適合として禁止する
- 候補に届かなかったものを、変形して同じ検証で再評価しない
- 自由パラメータは少なくする(例: 4個以下)。日付に依存するルールや、対象の手選びは禁止する

## 記録

| ファイル | 中身 |
| --- | --- |
| `trials.jsonl` / `registry.jsonl` | 全評価を自動で追記。データ・凍結ファイル・コードのハッシュ、split、指標、門の結果。手で書き換えない |
| `scratch.jsonl` | 下見。これも試行回数に数える |
| `adopted.json` | split ごとの採用状態と、取り消しの履歴(理由、試行の id)。取り消した名前は再採用しない |
| `holdout_audit.jsonl` | 封印テストを開けた記録。時刻、評価した版のハッシュ、何回目か。追記のみ |
| `tried.md` | 効かなかった考えと測定値。再検討するときは「何が変わったか」を書く |
| 「崩れた前提」の表 | 大きな改善が、どの前提を崩したときに出たか |

## 振り返り

5〜10ラウンドごと、またはセッションの終わりに書く。
- 効いた考え、効かなかった考え
- 偶然の可能性: 試行回数、補正後の有意性、効果の大きさとノイズ幅の比
- **同じ考えの言い換えになっていないか**: 別々に見える改善が、実は同じ考え(例: 直近の強さ)を別の形で測っているだけのことが多い。それは独立の証拠ではない
- 伸びの中身: 露出の増加、相場や環境の追い風、行動の頻度の変化で説明できないか
- 次の仮説の上位3つ
- ループ自体の摩擦(遅い評価、壊れたスクリプト、手作業)。見つけたら、コード、テスト、契約まで直す

## 打ち切りと方針転換

数を埋めるために回し続けない。

- **頭打ち**: 直近 K ラウンド(例: 5〜20)で採用なし、または最良の伸びが閾値未満
- **時間**: 1回のセッションは H 時間まで(例: 8時間)
- **ラウンド**: 上限 R(例: 200)
- **方針転換**: 一定時間(例: 60分)、または一定ラウンド門を通らなければ、調整や高速化をやめ、前提から違う方針を立てる。大きな改善は、書き出されていなかった前提を崩したときに出ることが多い。「崩れた前提」の表を、次の転換の根拠にする
- **系統のリセット**: 封印テストで不合格になったら、その系統を閉じる。戦略と記録は archive に移し、ループからは見えないようにする。試行回数のカウンタはリセットしない

止めるときは「区切り」を書く。止めた理由、効いたもの、効かなかったもの、次の仮説の上位3つ。

## 並列のエージェント

- 前提が重ならない方向に3台前後を振る。同じ方向に複数を当てない
- worktree で分ける。共有の作業ツリーでは、ブランチの切り替えでコミットが混ざる事故が起きる
- 各エージェントは worktree の中で実測し、勝ったときだけブランチにコミットする。本番への提出と push はさせない
- 依頼文には共通のブリーフを使う。含めるもの: 既知の否定結果(測定値つき)、打ち切りの条件、予算、時間の上限
- 本体は報告を鵜呑みにせず、自分で再測定してから取り込む
- 別々の版から出た改善は、足し算にならないことが多い。統合は別の担当に任せ、パラメータを実測で決め直させる

## よくある事故

- 採点器のスクリプトが、分割名の変更などで落ちていて、記録が書かれていなかった。分割や名前を変えたら、参照しているコードを総点検する
- 常駐のジョブが古いブランチから起動して失敗した。主ツリーは main に固定し、作業は worktree でする
- 未コミットのコードで作ったデータセットが、再現できなくなった
