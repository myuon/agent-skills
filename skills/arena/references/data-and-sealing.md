# データの用意と封印

## 分割

| 区間 | 用途 | エージェントから |
| --- | --- | --- |
| 設計用(train) | 仮説を作り、調整する | 自由に見てよい |
| 検証(valid) | 採用の判断 | keep を通った候補だけ。見た回数を数え、上限を置く |
| 封印テスト(holdout) | 本番前の最終確認 | 見えない。人間かリードが、事前登録の後に開ける |
| 前向き(forward) | 封印テストを開けた後に溜まる、真に未見のデータ | 記録だけ。判定は事前に決めた日に |

- **時系列は時間で切る**。ランダムに切ると未来の情報が混ざる
- **設計用を部分期間に分ける**(前半と後半など)。両方で大きく負けないことを門にすると、特定の期間だけの当たりを落とせる
- **検証は1つにしない**。walk-forward の複数の fold にする。train を拡大し、train と valid の間に空白(ラベルの窓の長さ以上)を置く。ラベルの窓が区間の終わりをまたぐ行は捨てる
- **評価区間を前に進める**。新しいデータが溜まったら新しい split を宣言し、採用済みのものを再評価する。切り直しの目安は1日1回まで。切り直すほど、試行回数の補正が甘くなる
- **事後の監査**: split の後に溜まった新データで、採用済みの改善が残っているかを定期的に見る。残っていなければ採用を取り消す。監査は非同期に走らせ、ループは待たせない。「新データが N 件溜まるまで採用を保留」という門を置くと、ループが止まる
- **split の切り直しの手順**: 新しい split には必ず新しいデータを含める。最初に基準線を測り、採用中のものを再確認する。その後、前の split で惜しかった案を、事前に書いたものだけ1回試す。1日1回より短い間隔での切り直しは「緩める変更」として申告する
- **相場や環境の局面が偏っていないか確かめる**。設計用が上昇一本調子だと、守りの仕組みが一度も試されない
- **期間を入れ替えた系統**: 旧系統の検証と学習の一部を入れ替えて、新しい系統として回す。独立に見つかる戦略が期間をまたいで一致するかを見る
  - 旧系統の戦略と記録は archive に移し、ループから見えなくする
  - 新しい検証の使用回数は0から数え、旧検証の使用回数は凍結する(リセットしない)
  - 検証期間の始まりに必要な履歴(特徴量の暖機)の扱いを先に決める
  - 前向きの記録で旧系統の戦略を使い続けるなら、archive に移しても動くようにしておく
- **系列を増やす**: 疑似世界、時間の窓、組み合わせの交差検証は [augmentation.md](augmentation.md)

## 封印の実装

約束でなく、コードと置き場所で守る。上ほど強い。

1. **別のマシン、または別の OS ユーザー**に封印データを置く。これだけが悪意まで防ぐ
2. **エージェントの作業場所に置かない**。ループは別クローンの sparse checkout や別ディレクトリで回し、封印データや、封印期間の結果を書いた文書がそこに存在しないようにする
3. **ファイルの保護**: 権限 700、変更不可フラグ(macOS の `chflags uchg`)、監査ログは追記のみ(`uappnd`)
4. **読み込み側で拒否する**: 境界の時刻をコードのリテラルで持ち(設定ファイルから読まない)、テストで固定する。境界より後のファイルは列挙も open もしない。範囲の指定が境界を越えたら例外を投げる。境界をまたぐ時間帯のファイルは丸ごと捨てる
5. **コマンドで拒否する**: ループから `holdout`、データの作り直し、検証の実行を呼べないようにする(目印ファイルや環境変数で判定)
6. **ツールの権限で拒否する**: Claude Code なら `.claude/settings.json` の deny で、封印パスの読み取りや `git show` などの履歴からの取り出しを拒否する
7. **候補コードの静的検査**: AST で import を許可リストに限り、ファイル IO、`eval`、`getattr`、dunder 属性を拒否する。候補が検証のラベルや封印データを直接読む抜け道をふさぐ

同じ OS ユーザーでの柵は、誤操作を防ぐだけで悪意は防げない。その限界は契約に書いておく。

## ループ専用の作業場所

ループを、封印データや検証の結果が存在しない場所で回す。
1. 別の clone を作り、ループに必要なファイルだけを sparse checkout で取り出す。凍結データは、検証・封印の期間を切り詰めた版を置く
2. エージェントの権限設定(Claude Code なら `.claude/settings.json` の deny)で、元のリポジトリ、封印ディレクトリ、過去の系統の archive と結果の文書を読めなくする
3. ループは別のプロセス(別のセッション)として起動する。サブエージェントは必ずこの作業場所を起点に起動する。元のリポジトリから起動すると権限設定が効かない
4. 起動前に、無害な指示で空打ちして、封印パスの `ls` や Read が拒否されることを確かめる
5. 作業場所の git 履歴に過去の結果が残っていないか確かめる

## 検証をループから見せない

文書で「検証を見ない」と約束しても、ループは設計中に検証を見て、その結果で設計を変える。期間を入れ替えた新しい系統でも再発した。
- 検証の実行と、検証期間を含む確認コマンドを、ループからは拒否する。検証はリード(主セッション)だけが、主張を事前登録した後に1回見る
- 記録される評価の外で、検証期間の値動きを集計したり日付を絞って調べたりすることも、指示文で禁止する
- 見てしまった分は「汚染済み」として記録し、その系統の検証の価値を割り引く

## 凍結と再現

- データは作成時のハッシュ(MANIFEST)で凍結する。作り方を変えたら版を上げ、別のデータセットにする
- データの作成は、コミット済みのコードからしか動かないようにする。未コミットのコードで作ったデータは、再現できないので使わない
- 全評価の記録に、データのハッシュ、凍結ファイルのハッシュ、git のコミットを残す
- 評価コード自体にも版(GATE_VERSION など)を付ける。版を上げたら、古い版で採用したものを再評価待ちにする

## 先読み(リーク)の検査

- 決定の時刻、約定の時刻、情報の締切を契約に書き、コードで強制する。例: t の引け後に決め、翌営業日の始値で約定。情報は約定日の 9:00 まで
- 時点を強制するコンテキスト(`ctx`)経由でしかデータを渡さず、将来のデータに届かないようにする
- 自動の検査: 時刻 t の特徴量が、t 以前のイベントだけに依存しているかを確かめる。全期間の平均での正規化などを落とせる
- 学習に渡すラベルも、窓が train の終わりを越える行は欠損にする
- LLM を特徴量やラベル付けに使うときは、モデルの知識の締切より後のデータだけで評価する。それ以前のデータでは、LLM が結果を知っている可能性がある
- 生存者バイアス: 上場廃止や欠損した対象を含むデータを使う。使えなければ、その限界を書く
