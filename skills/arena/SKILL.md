# Arena

エージェントに手順を細かく指示するより、正直な採点器を渡して自由に試させるほうが伸びる。ただし、自由に探索させるほど、エージェントは採点器の穴や検証データの偶然を見つけてくる。このスキルの目的は、**スコアの伸びを本物の伸びに保つこと**。

## 原則

1. **アリーナの外にある「本物」を最初に決める**。本物とは、お金、順位、本番の成績のこと。アリーナのスコアは、本物の代理でしかない
2. **スコアを本物に近づける**。予測精度より期待損益、税引き前より税引き後、順位の予測より期待クリック数を使う。代理と本物のずれは、必ずどこかで突かれる
3. **エージェントが変えてよい範囲を1か所に絞る**。データ、分割、採点器、門は「変えない側」に置き、コードで凍結する
4. **約束でなくコードで守る**。「検証データを見ない」「封印を開けない」を文書に書くだけでは破られる。拒否するコマンド、ハッシュの照合、ファイルの隔離で守る
5. **全試行を記録し、試行回数で割り引く**。下見も1回と数える。多く試すほど、最良の結果はまぐれに近づく
6. **封印テストは1回ずつ、主張を事前登録してから開ける**。開けた区間は、その系統にとって未見ではなくなる
7. **アリーナのスコアと本物の差を一番目立つ場所に出す**。スコアが伸びても差が開くなら、それは改善ではない
8. **ループを止めない**。新しいデータ待ちや人間の返事待ちを、採用やループ再開の条件にしない。監査は後から非同期に走らせ、負けたら採用を取り消す。データが足りなければ、待つのでなく今のデータで系列を増やす
9. **ロバストさは門で入れ、主スコアは削らない**。主スコアに最悪値や下位の値を使うと、リスクを取らない候補が勝つ。主スコアは中央値などにし、床と上限は門にする

## 手順

### 1. 契約を書く

アリーナごとに1枚の契約(`docs/arena.md` など)を書き、回し始める前にコミットする。雛形は [references/contract.md](references/contract.md)。

決める項目は次のとおり。
- 本物の物差し
- スコアの定義
- 比べる基準線(何もしない場合、素朴な方法)
- 変えてよい範囲
- データの分割と封印
- 採用の門
- 封印テストを開ける回数の上限
- 打ち切りの条件

契約を変えるときは版を上げる。基準を緩める変更は人間が承認する。厳しくする変更と、本物に近づける変更は、エージェントが自分で入れてよい。

### 2. データを用意して封印する

[references/data-and-sealing.md](references/data-and-sealing.md)

- 分割は、設計用・検証・封印テストの3つ。時系列データは時間で切り、前向きに進める
- 封印テストはエージェントの作業場所に置かない。読めないようにする
- データはハッシュで凍結し、作り方を変えたら別の版にする
- 先読みの検査を自動化する。時刻 t の特徴量は、時刻 t 以前の情報だけで作る

### 2b. データの系列を増やす

[references/augmentation.md](references/augmentation.md)

1本の歴史だけで採点すると、少数の対象や1つの局面への依存を見抜けない。元の複雑さを壊さずに、疑似世界(部分集合、勝ち対象を外す、偽の対象を足す)、時間の窓、組み合わせの交差検証で系列を増やし、「どの世界・どの時期でも勝つか」を採点に入れる。

### 3. 採点器と採用の門を作る

[references/scorer-and-gates.md](references/scorer-and-gates.md)

- 比較は対応ありで行う。同じ seed、同じ fold、同じ期間で比べ、差の標準誤差を出す
- 基準線は、何もしない基準線に加えて、強くて単純な基準線(等ウェイトなど)を必ず門に入れる。弱い基準線にだけ勝って「頑健」と報告しない
- 門の例:
  - 基準線に勝つ
  - 差がノイズ幅の2倍以上ある
  - 試行回数で補正しても有意(Bonferroni、Deflated Sharpe)
  - fold の過半数と、最新の fold で勝つ
  - パラメータの近傍でも勝つ
  - ストレス条件(コスト増、不利な約定、税)でも勝つ
  - 本物の物差し(お金)の門も通る
- 門は `eval` や `log-round` のコードに入れ、通らなければ記録も採用もできないようにする
- 空の検定をする。同じものどうしを比べ、門が誤って「改善」と言わないか確かめる

### 4. 本物の評価が遅いときは、2速にする

[references/surrogate.md](references/surrogate.md)

本物の結果が数週間かかる題材(SEO、集客、新製品)では、速い模擬評価器と、遅い本物の評価を交互に回す。
- 模擬評価器(代理モデル)を、最適化の目的関数にしない。目的関数は、より本物に近い審査(LLM の審査団での対比較など)にし、代理モデルの点は記録とふるい分けにだけ使う。採否は本物の評価で決める
- 毎周、模擬の予測と本物の結果の相関を「アリーナの信頼度」として記録する
- 本物の結果を模擬評価器の学習データに戻し、信頼度の低い特徴は最適化させない

### 5. ループを回す

[references/loop.md](references/loop.md)

- 1ラウンドで試す仮説は1つ。宣言(仮説、変更点、判定基準)を評価の前に書く
- 区切りは時間か頭打ちで決め、ラウンド数で区切らない。ただし最低限は回す(例: 50ラウンド)。少ないラウンドでは、採点器の癖も候補の伸びも見えない
- 1つの仮説の変種は3つまで。効かなかった後の強さの再調整は、検証への過適合として禁止する
- 数ラウンドごとに振り返る。効いた考え、効かなかった考え、偶然の可能性、通算の試行回数、そして同じ考えの言い換えになっていないかを見る
- 内省を仕組みにする: 仮説の種類ごとの採用率の台帳、同じ考えの言い換えの表、ループに関わらない点検役。ループ担当は手順やルールを自分で変えず、提案として残す
- 打ち切りの条件:
  - 頭打ち: 直近 K ラウンドで採用なし、または改善がノイズ幅以下。頭打ちの判定を学習期間の成績だけで行うと、それ自体が学習期間への合わせ込みになる
  - 試しすぎ: 試行回数で補正した後に必要な z が3を超えたら、その split は打ち切り、新しいデータを含めて切り直す
  - 時間の上限、ラウンドの上限
  - 方針転換: 一定時間門を通らなければ、調整をやめて前提から違う方向を試す
- 並列のエージェントは、前提の違う方向に振る。worktree で分け、報告は本体で再測定してから取り込む

### 6. 人間に見せる

[references/artifact.md](references/artifact.md)

ダッシュボードは1枚にして、同じ場所を更新し続ける。調査用のものとは分け、アリーナ専用にする。一番上に置くもの:
- いま何待ちか(何も待っていなければ、それも書く)
- 人間に頼みたいこと
- アリーナのスコアと、封印テスト・前向き記録・本物の評価との差
- 通算の試行回数と、補正後の有意性
- 打ち切りまでの残り(ラウンド、時間、封印テストを開けられる残り回数)

## 本番に出す前の確認

- [ ] 主張を事前登録してから、封印テストを1回だけ開けた
- [ ] 前向きの記録(紙上の売買、本番に近いシャドー運用)で、事前に決めた期間と基準を満たした
- [ ] 長い期間や別の局面(下落相場、別の季節、別のデータ源)でも崩れない
- [ ] スコアの伸びの中身を説明できる(露出の増加や、相場の追い風だけではない)
- [ ] 試行回数で補正しても残る
- [ ] シミュレータの楽観的な仮定を列挙し、それぞれに悲観側のストレスを掛けた
- [ ] 疑似世界と時間の窓のどこでも、同じ世界の基準線に勝つ。利益が少数の対象や1つの期間に集中していない

## 落とし穴

実際のアリーナで起きた失敗は [references/pitfalls.md](references/pitfalls.md) にまとめた。新しいアリーナを作る前に一度読む。
